# HTTP value receipt acceptance

Live acceptance is pending. #67 prepares the existing SHA256/UTF-8 byte receipt before setting a value or emitting input/change events. If Web Crypto cannot prepare that receipt, the attempt returns the constant `value_receipt_unavailable` error before mutation; it does not return the input or an underlying digest error. Use HTTPS or a trusted loopback origin and obtain a fresh snapshot before retrying. Other DOM action failures retain their existing semantics; this change does not add effect verification or automatic retry.

Use the controlled `chrome/fixtures/http-value-receipts.html` (SHA256 `29c1bd4c97bfb35091c06260198b676bfae913df3e7117983052c8cec72cf62a`) in an owned Chrome for Testing profile with immutable packaged scripts/private broker and explicit temporary tab enablement plus exact-document pairing. The first and second inputs are both named **Shared message**, initially `First initial ✓` and `Second initial 🪷`; each has independent visible input/change counters at zero. Save page origin/security/subtle availability, exact candidate identities, pair/read/action receipts, independent DOM values/counters and rendered screenshots. Keep daily browsers, installed Nova/Bodhi, TCC and production host registrations unchanged.

1. On an ordinary non-loopback HTTP origin, attempt to set the second exact input to `Updated 中文 🪷 ✓` from a fresh snapshot. Confirm the typed receipt-unavailable result, no input plaintext in the action result, both initial values unchanged and every event counter still zero. A second attempt with the old snapshot must fail; a new semantic read must still show the initial values. Retain the reviewed #66 baseline separately to demonstrate its write-then-error behavior.
2. On loopback HTTP (or HTTPS), explicitly enable and pair the current document, then set the second exact input from a fresh snapshot. Verify the original SHA256 and UTF-8-byte acknowledgement independently, the first input unchanged, the second input updated and only its input/change counters incremented once. Confirm the new value in both rendered UI and a subsequent semantic read. Do not weaken browser security or substitute a plaintext/hash fallback.
3. Release through the popup, enable and pair the same document again, then confirm a fresh authorized write succeeds. Retain the old route/snapshot rejection and new epoch evidence. Deterministic Node tests additionally hold digest preparation while revoking/re-enabling, changing document routes, invalidating through successful/failed reads, consuming a newer action, or making the target private/disconnected. Old attempts must not write or emit events.

The content handler consumes a snapshot before receipt preparation. One ephemeral revision covers existing reads, route replacement and revocation/unload; a sync callback checks it after digest preparation, then the runtime checks the exact target again before mutation. Repeated registration of an unchanged route does not cancel the attempt. Worker native/popup release, disconnect and actual content-transport revocation reuse the existing `revoke_access` message for the captured old exact document; release responses wait for that delivery attempt, bounded by the existing 10-second content deadline. Tests resume held hashes after forwarded invalidation, check same-document re-pairing/protection of a newly paired document, and establish bounded release/timeout responses when the document never answers. Cross-process revocation delivery is best effort, not a global atomic transaction; the existing transport-ambiguity boundary remains.

Independent review found the initial delivery attempt had no deadline. Three regressions failed before repair, for native release, popup release and content-timeout completion; the helper now bounds only that existing message attempt and clears its timer. [Chrome's tabs messaging API](https://developer.chrome.com/docs/extensions/reference/api/tabs#method-sendMessage) resolves on a content response and does not supply this application's deadline.

This slice changes no shadow/frame traversal, native wire protocol, hash service, dependency, provider mapping, signing or trusted-input contract. [Web Crypto's subtle attribute](https://www.w3.org/TR/webcrypto/#crypto-interface) requires a secure context; [Secure Contexts](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy) defines potentially trustworthy loopback origins.
